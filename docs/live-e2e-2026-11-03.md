# Live end-to-end probe — 2026-11-03

The test suite is fixture-driven: `tests/` runs the real runner against
`decide.backends.fixture` and replayed/faked op backends, so it proves the engine
but not the *shipped* path. This run proves the shipped path: HTTP ingress →
inspector → plan → decide wall → ops wall → response contract, with d1-3B
answering over `/v1/systemone` on a real socket.

Tool: `bench/live_e2e.py` (new). Offline contract coverage:
`tests/test_live_e2e_contract.py` (22 cases). Regression tests for every defect
below: `tests/test_live_e2e_regressions.py` (13 cases). Suite: **361 passed,
159 subtests** (`python3 -m pytest tests/ -q`). The L1 fixture's third file is
`server-out.txt` rather than `server.log` only because `*.log` is gitignored.
*(361/159 is the count when this run was made. As of 2026-11-03 16:14 EST at
`a105d50` the same command reports **722 passed, 388 subtests**.)*

Contract checks applied to every body (`check_contract`, spec §3 field by field):
`status ∈ {done,need_input,error,plan}`; `hops` present and a list; each hop
carries `step/op/ms/conf/artifact_summary` with `ms`/`conf` numeric and
`0 ≤ conf ≤ 1`; `confidence` numeric in range; `degraded` boolean; `assumptions`
a list of strings; `sources` a list when present; `question` well-formed for
`need_input`; `error` present iff `status=="error"`; and every hop `op` is a
registered op or one of the runner's own ask-back records. Case-level checks make
the hops correspond to reality: the `filesys_read` hop's
`artifact_summary` must be a prefix of the bytes of a file that exists, the
`decide_pick` hop must name the file that was read, and the L2 extract hop's
queries must carry an intent term.

`sources` was absent on every case. It is optional in spec §3 and no template
populates it — the "assemble" step of spec §7 is not implemented (P4). The probe
checks the field's type when present and reports the absence rather than
inventing a contract requirement.

*(That was true of this run and is no longer true of the tree, as of 2026-11-03:
`digest_assemble` landed — `ops/research/assemble.py`, the `digest` step at
`planner/templates/research.py:103` — so a research plan ends in a digest that
carries `sources`, and the L2 case's terminal hop is `digest`, not `web_fetch`.
The absence recorded above is a property of the 03:08 run.)*

## Defects found and fixed

Every one was found by running the probe, is fixed minimally, and has a
regression test that fails on the old code (verified by reverting each fix and
re-running its test — all ten reversions were caught).

### 1. A picked relative path was read against the service's cwd, not the caller's

`service/ti/planner/templates/disk_lookup.py:49` built the read step with no
frame, and `service/ti/ops/filesys/impl.py:82` opened `params["path"]` as given.
`filesys_glob` reports hits relative to the **digest** cwd, so the read resolved
against the *service process's* cwd — which `pi-extension/src/lifecycle.ts:38`
pins to the repo root. Live symptom (first probe run, `digest.cwd` elsewhere):

```
status error   hops: filesys_glob, decide_pick (conf 0.967)
error  "[Errno 2] No such file or directory: 'notes.md'"
```

The whole L1 slot-fill path was broken for every pi session whose cwd was not the
service's, which is nearly all of them.

Fix: `filesys_read` takes an optional `cwd` and joins a relative `path` onto it
(absolute paths untouched); the L1 plan passes the digest cwd it globbed in.
Test: `L1ReadFrameTest` (both the relative and the absolute case).

### 2. The L2 research plan named two ops that do not exist

`service/ti/planner/templates/research.py:19,23` used `__decide_extract__` and
`__decide_pick__` — P0 placeholder names. Registered ops are `decide_extract` /
`decide_pick`, so the runner's `get_op` raised at the first step:

```
status error  hops: []   error "unknown op '__decide_extract__'; known: [...]"
```

Every intent containing "research" or "compare" — spec §7's headline pipeline —
died before running anything.

Fix: name the registered ops. Test:
`ResearchPlanTest::test_every_step_of_the_research_plan_is_a_registered_op`
(also resolves each step's op through `get_op`).

### 3. The research extractor never saw the intent

`service/ti/ops/decisions.py:65` declared only `instructions`/`source_artifact`/
`count`, and `run_extract` built its state from `source_artifact` (absent on the
research `queries` step). The runner already merges the intent in as
`intent_context` (`core/runner.run_plan`), but an undeclared key lands in `soft`,
which `run_op_with_log` logs and then drops. So the extractor mined its own
instruction text:

```
decide_extract 0.2ms conf 0.72 → ['research current stable', 'research current', 'research', 'research stable']
```

for the intent `research the current stable python version` — "python" and
"version" never made it into a query, by construction.

Fix: declare `intent_context` optional and fold it into the state's context
(`{"intent": …, "source": …}`); `rule_extract` flattens values, so the intent is
now payload. Test: `ResearchPlanTest::test_the_extract_step_is_told_the_intent`.

### 4. A gate block over HTTP degraded instead of asking

`service/ti/service_entry.py` called `use_tool(body, dry=dry)` from
`http/api.py`, i.e. with no `on_ask`, so `_handle_block` hit `MaxAsksReached`,
the runner fell through to "best guess", and the response was
`status:"done", degraded:true`. `need_input` was unreachable over HTTP except by
exhausting the hop budget (`run_plan`'s `finish("need_input" if not hops …)`),
which cannot happen with a non-empty plan. Spec §4's ask-back — the whole point
of triggers 1–4 — had no path to the caller, while the extension's renderer and
the response schema already had a `question` branch waiting for it.

Fix: `use_tool(..., ask_via_response: bool)`; `_run_steps` records the question
when the run has no channel and the transport sets the flag
(`http/api.py:47`, `not dry`), and the response becomes `need_input` +
`question{kind,question,options}` while still carrying the degraded best guess.
Direct callers that pass neither `on_ask` nor the flag keep the old behaviour
(`tests/test_conf_degraded.py` and `test_cascade.py` still pin it). Test:
`AskBackChannelTest` (flag on → `need_input` with all five candidates; flag off →
`done`+`degraded`) and `HttpRouteTest::test_the_route_carries_need_input_and_then_the_answer`
over a real `ThreadingHTTPServer`.

### 5. `params.answer` was never consumed, so the loop could not close

The extension tells the LLM to "call useTool again … put the answer in
params.answer" (`pi-extension/src/index.ts`, need_input branch), and nothing read
that key. An answer rode along as soft context — which `run_op_with_log` logs and
ops never see — so the retry re-planned from scratch, the same gate blocked on
the same low-confidence pick, and the caller was told to answer a question it had
already answered.

Fix: when there is no `on_ask` and `params.answer` is set, that answer *is* the
channel — the run continues with a constant reply, `_handle_block` re-writes the
gated artifact at conf 0.9, and the response is `done` with an
`askback.resolved` hop. Tests:
`AskBackChannelTest::test_the_answer_resolves_the_gate_the_question_named`,
`HttpRouteTest::test_the_route_carries_need_input_and_then_the_answer`.

### 6. The question offered the rejected pick as its only option

`service/ti/core/runner.py:143` built the options from the *last* artifact of
kind `path_list|picked_items|url_list`. After a blocked pick that is
`picked_file` — `picked_items` holds exactly one item — so the live question was:

```
question (choice): Step 'content' blocked: artifact 'picked_file' conf 0.26 below gate. Answer to resolve:
  report-final.md          <- the answer the gate had just rejected, and the only option
```

A choice question with one option is not answerable, and spec §4 requires
"choice (candidates listed)".

Fix: prefer the enumeration (`path_list`/`url_list`), fall back to a
`picked_items` only when no enumeration is in the store. Test:
`AskBackChannelTest::test_the_options_are_the_enumeration_not_the_rejected_pick`.

### 7. A URL candidate's option id was a dict repr

Same block: `str(it if not isinstance(it, dict) else it.get("id", it))`. URL
candidates are `{title, url, snippet, sources, source_count, queries}` dicts with
no `id`, so the option id became a Python dict repr. Reverted offline, the
`_handle_block` path emits:

```
PRE-FIX option id (80 chars for a 3-field hit): {'title': 'quantization guide', 'url': 'https://example.test/q', 'snippet': 's'}
```

— 80 characters for a synthetic three-field hit; a real `web_search` hit (title,
snippet, sources, source_count, queries) is several hundred, and not something a
caller can answer with.

Fix: `_option_id` — `id`, `url`, `path`, `name`, `title`, else `str(item)`. The
live L2 question now lists plain URLs. Test:
`AskBackChannelTest::test_a_url_candidate_offers_its_url_as_the_option_id`.

### 8. An empty candidate list blamed the decide backend

`decide_pick` asked the backend to choose among zero candidates. d1 abstains,
`pair` raises, and the response for a nonexistent cwd was:

```
status error  error "pair: no stage produced a choice"   hops: filesys_glob only
```

which names a backend failure for what is an empty directory.

Fix: raise `decide_pick: 'candidates' has no candidates to choose from — the
previous step found nothing` when the criteria set is empty
(`ops/decisions.py:96`). Test: `EmptyCandidateTest`.

### 9. `/health` could not say which backend answered

`GET /health` returned `{status, ops, conf}`. A `done` from the replay fixture
and a `done` from d1-3B are the same body, so nothing — least of all a probe —
could tell a live run from a fixture one. That is exactly the "silently passes
against nothing" failure the probe exists to prevent.

Fix: `/health` also reports `decide` (the `backends_in_use` map) and `cascade`
(the flag). The probe refuses a run whose `choice` backend is a replay backend,
and prints the map in its header and its verdict line. `ServiceHealth` in
`pi-extension/src/bridge.ts` reads named fields and ignores extras, so no TS
change was needed (verified by `tsc --noEmit`, below). Test:
`HttpRouteTest::test_health_names_the_decide_backends`, plus
`tests/test_live_e2e_contract.py::BackendEvidenceTest`.

### 10. The shipped decide timeout is a coin flip for an L2 pick on this box

Not a code defect — a measurement the probe had to survive to be useful, and one
the operator should know before trusting P4 numbers. `decide.d1_systemone.timeout_s`
ships as 30. The L2 pick decision is ~509 tokens of prefill; on this box that
measured 20.5 s in one run and **61 s in another** (same request, same config, a
concurrent GPU/Vulkan llama-server on the same machine). At 30 s the second run
raised a transport timeout inside stage 1, `pair` escalated to stage 2, stage 2
had no API key, and the plan ended as:

```
status: error   hops: [decide_extract 0.72, web_search 1.0]   wall 31421 ms
error:  "pair: no stage produced a choice"
```

after 30 s of work with 40 search hits in hand. Two follow-ups, neither of which
this task should decide alone: the timeout belongs above a shared box's worst
case (or the pick's state must shrink — `decide.max_candidates` is the latency
knob, 6 today), and a stage-1 timeout should arguably degrade to "pick the
lexically best candidate" instead of aborting a plan that already paid for the
search. The probe's `--serve` sets `--decide-timeout 120` for exactly this
reason, and the flag's help says so.

## Defects found and *not* fixed (quality, not contract)

Recorded rather than repaired — each is a tuning claim, not a break, and the task
was minimal fixes for observed failures.

1. **Research queries lead with the routing verb.** `rule_extract`'s query mode
   treats "research"/"compare" as salient, so
   `research llama.cpp quantization options …` yields
   `['research llama.cpp quantization', 'research llama.cpp', 'research', …]`.
   The first query still carries the topic, so search works; one of four queries
   ("research") is wasted. Fix belongs in `rule_extract`'s stopwords or the
   template's instructions, with the P4 query-quality work.
2. **`ask_available` reads `false` on an HTTP `need_input` hop.** The runner sets
   it only after an in-process `on_ask` returns; over HTTP the question does
   reach the caller, in the response body. The hops log — the finetune dataset —
   therefore under-reports answered asks. Left as is because the flag is defined
   by the runner's own channel, and changing it would touch the runner's ask
   bookkeeping beyond the fix.
3. **`sources` is never populated.** Spec §7's "assemble" step (per-source claim
   digest + link) does not exist; the research plan ends at `pages`.
   *(Closed 2026-11-03: the step exists — `digest_assemble` — and populates
   `sources`; see the note in the contract section above.)*
4. **Ask-back option descriptions are empty.** `options[].desc` is always `""`,
   so an LLM choosing among paths/URLs gets ids only. The ids are answerable, so
   the loop closes; descriptions are a quality item, not a contract one.

### The recorded run predates auth and cannot be replayed by the script as it stood

**Status, written 2026-11-03 16:20 EST at `a105d50`.** The gap below is in the
*driver*, not in the service: the probe sends no token at HEAD, so running it
measures nothing. The `5/5` table above is a measurement of the 03:08 stack — taken
before auth existed — and is kept as that, not as a standing claim about the probe
or about the tree.

Re-run at `ca7ffec` (2026-11-03 15:5x EST): `0/4 cases passed`, HTTP 401.

The driver could not authenticate that evening. It sent no `Authorization` header
at all — `grep -n "token\|Authorization\|Bearer" bench/live_e2e.py` matched one
comment and nothing else — while the shipped service requires the shared token on
every POST (`service/ti/http/auth.py`; "There is no 'no token' mode"). Auth landed
in `5dc537f` at 03:17:30, **8 m 45 s after** the `5/5` run recorded above at
03:08:45, and `bench/live_e2e.py` was last edited at 04:27:49 (`e52c86b`) without
picking it up. So the recorded run predates auth by nine minutes and the script
could not reach the service it describes.

```
$ python3 bench/live_e2e.py --serve --skip-l2
t 1 l0_passthrough_read       -              -    0       1.6  FAIL
...
l0_passthrough_read: L0: params fully specify a tool — no decision, real read
  FAIL transport failed: HTTPError: HTTP Error 401: Unauthorized

0/4 cases passed (choice backend: pair)
stack stopped (2 process group(s): llama-server + service)
```

The stack itself starts correctly: `llama-server` serves `d1-3B-Q4_K_M.gguf`
(Q4_K - Medium, `/props` asserted) on `:8099` from the fall-back path
`~/toolInterfacer/{models,extern}`, the service answers `/health` on `:1114` with
`choice=pair noul=fixture extract=rule_extract`, and both process groups are torn
down. Two things then, in order.

**First, the probe's contract checks are no longer the reason it fails.**
`check_contract` used to demand a `confidence` on every `done` and `need_input`
body and a numeric `conf` on every hop; the service by then omitted `confidence`
when nothing was measured and reported `conf: None` for a rule extractor, so the
probe would have failed correct bodies as well as refused ones. That half is
fixed at HEAD (`bench/live_e2e.py:188,209-219`: `confidence` is optional for
every status, a null hop conf is allowed), so the token is now the only thing
between this probe and a real run.

**Second, the token is being wired, on another branch.** `p2-regress` @ `ae9961e`
(2026-11-03 16:07:17, "fix(bench): the probes survive auth and a bad artifact")
makes every POST carry the token — resolved by the service's own
`service/ti/http/auth.py`, not a copy of the rule — has `--serve` hand the child
it spawns the same value, adds `--token` for attaching to a service whose token
was set by hand, and exits `2` on a 401 so a table of refused cases can never
read as a score. It is not on `main` at `a105d50`.

What is still open, and what would settle it: **whether the five cases reproduce
once the token is wired.** Until then, the honest reading of the `5/5` row is
"that stack, that evening, before auth", and the `conf` column beside it is a
body shape the service no longer emits (see the note under the run table).
