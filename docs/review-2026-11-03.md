## Blockers

### B1. The L2 research template has never run: its steps name ops that do not exist
`service/ti/planner/templates/research.py:19,23` — `op="__decide_extract__"` and
`op="__decide_pick__"`. The registry has `decide_extract` / `decide_pick`
(`service/ti/ops/decisions.py:65,78`); nothing maps the underscored names.
`inspector.inspect` routes any intent containing "research" or "compare" to this
template (`planner/inspector.py:15`), so the project's headline compound intent fails
at step 0 on every call — including the P4 acceptance criterion in the spec.

```
$ python3 -c "from ti.service_entry import use_tool; ..."
--- research intent
{"status": "error", "confidence": 1.0, "error": "\"unknown op '__decide_extract__'; known: ['decide_extract', 'decide_pick', 'filesys_glob', 'filesys_grep', 'filesys_read', 'reddit_digest', 'web_fetch', 'web_search']"}
    hops: []
```

Minimal fix: use the registered names, and add one test that runs
`use_tool({"intent": "research ..."})` with the fixture backend and asserts a non-error
status. No template has such a test today (see §Test audit).

### B2. A run that measured nothing reports `confidence: 1.0` — including a hard error
`service/ti/service_entry.py:131-132` (in `_route_conf`, defined at `:111`):

```python
    if not signal:
        return 1.0
```

`_route_conf` returns 1.0 when no hop carried a measurement. That covers the error run
quoted in B1 (`status: "error"`, `hops: []`, `confidence: 1.0`), and
`_passthrough` hardcodes the same number for L0 (`service_entry.py:67,70`). The
extension renders it verbatim — `route conf 1.00` (`pi-extension/src/index.ts:69`) — so
the one number a caller uses to decide whether to trust an unattended result is at its
maximum exactly when there is no evidence. `Artifact.conf` compounds it by defaulting
to `1.0` (`core/artifacts.py:19`), and `filesys_*` ops return 1.0 unconditionally
(`ops/filesys/impl.py:77,87,109`).

Minimal fix: return `None` when `signal` is empty and omit the field in the response
(`confidence` is already `Type.Optional` in the contract); drop the 1.0 from
`_passthrough` and from the filesys ops, which return a *deterministic* result, not a
decision.

### B3. A one-entry probability vector is read as p_max 1.0, so `tau` can never fire
`service/ti/decide/pair.py:232-233` and `decide/cascade.py:189-190`:

```python
    if len(probs) == 1:
        return 1.0  # single option owns all mass; conf_scale.d1_conf uses the same K<2 rule
```

`d1_conf`'s K<2 rule is a *server-side* sentinel for a degenerate question; imported
into a gate it converts "the model expressed no distribution" into "maximum
confidence". A stage that answers with one probability — which is exactly the shape
`openrouter.choice` returns by design (`backends/openrouter.py:149`) — always
clears `tau`, never escalates, and (in the cascade) is handed the fitted commit
precision as its reported confidence:

```
--- pair, stage1 offers one option at 0.02: choice='only' conf=0.02 stage='stage1'
    reason='confident' escalated=False stage1_p_max=1.0 stage2_calls=0
--- cascade, stage1 one option at 0.02: choice='only' conf=0.87 path='stage1' stage2_calls=0
```

So a 0.02-confident answer is reported downstream as 0.87, above `gate_slot` 0.7, and
the next step executes unattended. `tests/test_pair.py:122-129`
(`test_a_single_option_vector_owns_all_mass`) pins this as intended.

Minimal fix: treat `len(probs) < 2` as "no decision" (raise, exactly as
`_require_choice` already does for a missing choice) rather than as p_max 1.0; then
delete the test that asserts the old rule.

### B4. An unauthenticated POST reaches arbitrary file reads, arbitrary-root walks, and a caller-supplied regex that hangs the worker
`service/ti/http/api.py:24-48` parses any JSON body and hands it to `use_tool`; no
token, no origin check, and `params.tool` + `params.args` is the documented L0 route
(`service_entry.py:54-72`). Every op is therefore reachable with arguments of the
caller's choosing:

```
== 1. L0 passthrough reads any file the process can read
(200, {'status': 'done', 'result': 'laptop\n', ..., 'confidence': 1.0,
       'hops': [{'step': 'L0', 'op': 'filesys_read', ...}]})
== 2. L0 passthrough globs any root the caller names
200 {"status": "done", "result": ["passwd", "passwd-"], ...}
```

`filesys_glob`'s walk root is also caller-controlled through `digest.cwd` and
`params.path` (`ops/filesys/impl.py:31-33,63-70`, `planner/scope.py:52-56,79-84`) with no
depth, hit or time cap on the walk. And `filesys_grep` compiles the caller's string as
a regex (`impl.py:93`) with no timeout:

```
$ timeout 25 python3 proof_redos.py   # pattern "(a+)+$" over a 41-byte file
exit=124 (still running when killed)
```

One thread of the `ThreadingHTTPServer` is lost per request, permanently. On this box
the walk root matters more than the regex: an `os.walk` rooted at a directory that
contains the sshfs mount blocks in uninterruptible sleep and cannot be killed.

Minimal fix: an allowlist of ops usable from L0 (`filesys_read/glob/grep` need not be
reachable from an HTTP body), a required shared token compared in `do_POST`, a
realpath confinement check against the run's `cwd`, a hit cap and a deadline in
`_walk`, and `re` patterns rejected or run against a bounded line length.

### B5. The decision model's candidate list is not bounded; the configured state budget does not apply to it
`service/ti/ops/decisions.py:52-63` builds `criteria` from `title + " :: " + snippet`
with no clip, and `:87` passes it straight to the backend. `guard_state` bounds
`state` only; the architecture doc calls this "the two-line guarantee".

```
guard_state-bounded decide state: 51 chars
unbounded criteria handed to the backend: 12000144 chars (~3000036 tokens at 4 chars/token)
state_max_tokens = 2000 -> budget 8000 chars
```

The budget exists because prefill is the latency lever and is measured at ~19 ms/token
on this hardware (`docs/testing.md`); a 12 MB candidate set is not a slow decision, it
is a wedged service. The op docstring at `decisions.py:92-94` states the opposite of
what the code does.

Minimal fix: run `criteria` through the same clip (`DESC_CHARS`, and a total-bytes cap)
before `backend.choice(...)`, and add a test that asserts the *criteria* size, not just
the state size (`tests/test_context_bound.py:213` asserts only the state).

## Majors

1. **Ask-back is not wired to the transport, and a blocked gate does not block.**
   `api.py:34-39` calls `use_tool(body, dry=dry)` with no `on_ask`, so
   `service_entry.py:85` raises `MaxAsksReached` on every prompt; `_handle_block`
   returns False and `runner.py:78-85` then **runs the blocked step anyway** with a note
   in `assumptions`. Consequence: `gate_slot` decides what gets *annotated*, never what
   executes, and `status:"need_input"` is unreachable except with `max_hops: 0`
   (`runner.py:73`). Three of the four ask-back triggers in spec §4 have no
   implementation; the fourth (slot gate) cannot ask. The extension nonetheless renders a
   full need_input path (`pi-extension/src/index.ts:100`) and the tool's prompt
   guideline tells the model to answer one (`index.ts:166`).
2. **`mode:"raw"` is a no-op, and the truncation notice points the model at it.**
   Server side `mode` is only compared against `"plan"` (`service_entry.py:37`); a raw
   call returns a byte-identical body once timing fields are removed (measured). Client
   side, `truncate()` at `index.ts:62-65` is applied to every `done` result (`index.ts:114`)
   at 1500 chars, and its own message says *"call useTool with mode:"raw" … for the full
   content"* — which cannot work. The only effect of `"raw"` is a 240 s timeout
   (`index.ts:204`).
3. **A body that is not JSON takes down the connection with a traceback.**
   `api.py:25-26` is outside the try in `_use_tool`, so `json.loads` and
   `int(Content-Length)` raise into `BaseHTTPRequestHandler`:
   ```
   == 3. a body that is not JSON
   ('EXC', "RemoteDisconnected('Remote end closed connection without response')")
   ... json.decoder.JSONDecodeError ... in do_POST
   ```
   The module docstring claims errors are surfaced "as structured error, not a 500
   hang".
4. **`max_seconds` is checked only between hops, and a budget stop reports success.**
   `runner.py:67-73`; a single op is unbounded (a `web_fetch` step is one hop for N URLs
   × `cli_timeout_s`):
   ```
   max_seconds=1.0, two 3s hops -> wall 3.0s, status=done, degraded=True,
   assumptions=['budget stop: wall clock 1.0s exceeded']
   hops executed: 1 result: None
   ```
   `status:"done"` with `result: null` is what the caller sees for a truncated run.
5. **A CLI timeout kills the child, not the process tree.** `ops/cli.py:141-144` uses
   `subprocess.run(timeout=…)`, which kills only the direct child; `docs/ops.md` §1
   claims "the process is killed, not orphaned". Measured: a CLI that backgrounds a
   `sleep` leaves both descendants alive after `CliTimeout`, so every timed-out
   `web-fetch` can leave its `curl`/`nodriver` subtree running.
6. **`reddit_digest` puts the intent into argv without `--`.** `ops/reddit/digest.py:123`
   builds `["search", query, "--json", "--limit", …]`, and `query` is the raw intent
   string (`templates/reddit_digest.py:12`). This contradicts `docs/ops.md` §1's blanket
   "`--` precedes the positional so a query that starts with `-` is not read as a flag";
   the two web ops do use `--` (`ops/web/search.py:127,132`, `ops/web/fetch.py:55`).
7. **Config keys that control nothing.** `policy.max_asks` is read by nobody (the budget
   block rules, `service_entry.py:80-86`); `policy.gate_noul` is dead
   (`policy/confidence.py:27`, used nowhere — no template declares a `post` gate, so
   `_noul_verifier` and the "verification failed twice" trigger are unreachable);
   `context.digest_max_tokens` is dead (`session_digest.py:9` mentions it, nothing reads
   it — the window is hardcoded `8 × 240`); `budget.max_hops` (24) can never bind against
   a maximum 4-step plan. `AskBack` (`policy/askback.py:28`) has no callers, and
   `packer.pack`/`trim` are dead outside `tests/test_skeleton.py`.
8. **Step params always win over the caller's, contrary to spec §3.**
   `runner.py:88` seeds `conforms` with `dict(step.params)` and `:102` merges
   `{**step.params, **llm_params, **conforms}`, so the step's values are re-applied last.
   Spec §3 ("`params` keys that match the resolved step's schema are injected as real
   args") is false for every key a step declares. Verified: a body
   `{"digest": {"cwd": …}, "params": {"cwd": "/etc", "pattern": "passwd*"}}` against a
   listing plan leaves the op with the planned `cwd`/`pattern` and **no assumption saying
   the caller's values were dropped**. The inline comment at `:101` describes the
   opposite behaviour.
9. **`filesys_grep` is a sample, and reports 1.0.** `impl.py:97` takes
   `files[:50]` in `os.walk` order per directory, `:104` stops at 200 hits, and `:109`
   returns 1.0 regardless. It also has no `SKIP_DIRS` (`:26` defines the set that only
   `_walk` at `:31-33` applies), so a
   repo-root grep reads `node_modules`, `.venv` and binaries. "Not found" and "not in
   the first 50 files" are indistinguishable to the caller.
10. **`filesys_read`'s `max_lines` does not bound I/O.** `impl.py:85` filters a full
    iteration instead of stopping it: reading 10 lines of a 99 MB file took 0.21 s
    (10 lines is microseconds) and read the whole file.
11. **Two confidence axes are compared against one gate without conversion.**
    `pair.tau` 0.90 is documented as p_max, while `gate_slot` 0.7 is compared against
    whatever the backend put in `answer.confidence` (`gates.py:37`), which for d1 is the
    server's `(p_max − 1/K)/(1 − 1/K)` and for `logit_read` is `1 − H/lnK`
    (`backends/logit_read.py:71-73`). `conf_scale.py` exists to fix exactly this and says
    of itself "Nothing here is wired into a default path yet". At `max_candidates` 6,
    `gate_slot` 0.7 is p_max ≈ 0.75 while `tau` 0.9 is p_max 0.90 — the two gates in the
    same run mean different things.
12. **The hop log has no bound and can break a call.** `hops/log.py:21-27` appends
    forever with no rotation, and `os.makedirs(os.path.dirname(self.path))` raises
    `FileNotFoundError` for a bare filename (`dirname → ""`), which surfaces as
    `status:"error"` for every call. Records carry `op_params` (paths, queries) truncated
    to 200 chars.

`tests/test_ops_web.py` runs the adapter as a real subprocess against

## Doc claims that are false, or that I could not verify

1. `spec/1.0-spec.md` §3: *"`mode:"raw"` returns un-summarized results (LLM escape
   hatch)."* — The service ignores `"raw"` (`service_entry.py:37`); the extension
   truncates at 1500 chars in every mode (`index.ts:62,114`).
2. `spec/1.0-spec.md` §3: *"`params` keys that match the resolved step's schema are
   injected as real args."* — They are discarded whenever the step declares the key

3. `spec/1.0-spec.md` §2 and §4: *"Ask-back: when confidence or verification fails after
   best-effort, the tool returns `{status:"need_input", question…}`"*, with four

9. `docs/ops.md` §1: *"A timeout raises `CliTimeout`; the process is killed, not
   orphaned."* — Only the direct child is killed (measured).
10. `docs/ops.md` §1: *"`--` precedes the positional so a query that starts with `-` is

12. `service/ti/ops/decisions.py:92-94` (code docstring, relied on by the architecture

## What is genuinely good

1. `ops/cli.py` is the right shape: one adapter, argv lists only, typed failures that
   distinguish "missing binary", "timeout", "no document" and "not JSON", and a `tolerate`
   list that keeps per-CLI exit-code knowledge in the op rather than in the adapter.
2. The `result_path`/`read_result` pair covers all three advert conventions the live CLIs
   actually use, and `_footer_value` is tolerant of the two-space indent the real
   `web-fetch` writes (`~/.pi/profiles/registry/web-fetch/scripts/web-fetch:343`).
3. `filesys._matched` documents and fixes a real bug (`fnmatch`'s `*` crossing `/`) and
   pins it with tests that would fail if the bug returned.
4. The offline evidence culture is real: `fake_cli.py` reproduces the wire contract
   without leaking test flags into production argv, the cascade/pair tests drive every
   documented policy branch, and `test_shape_heldout` asserts *exactly* its known misses
   instead of a flattering accuracy number.
5. `docs/decision-pair-vs-hosted.md` and `docs/model-sweep-consolidated.md` are the best
   thing in the repo: a correction notice that withdraws a wrong result, raw file names,
   n, and a stated decision rule. That standard is worth applying to the code docs, which
   currently overstate three separate guarantees (B5, §Doc claims 2 and 7).
