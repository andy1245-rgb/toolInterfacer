# The fusion arm — what it measures, what it fails, and what the review found

2026-11-10. Artifacts: `bench/results/fusion-2026-11-10/` (the pre-registered run) and
`bench/results/fusion-sensitivity-2026-11-10/` (the fold-rule sweep, summaries only). Both
recompute offline from the repo; no server was up. Conditions were written to
`fusion-2026-11-10/prereg.json` **before** the run.

## The pre-registered run

`fusion|member=sklearn_text~vectorizer=tfidf_word~clf=logreg~features=rules|weights=0.5`
against `recorded|arm=floor_a`, five folds, seeds 0/1/2/4/7, stratified.

| | |
|---|---|
| reference, the 3B replayed | **325/415 = 78.31%** |
| `r_fusion`, equal-weight mean | **351/415 = 84.58%**, fixed 37 / broke 11, exact McNemar **p = 0.000222** |
| delta by fold seed | +26, +23, +26, +25, +25 |
| ledger | extract +12, glob +7, grep +6, reddit +6, read +3, **web_fetch −3, web_search −5** |
| `r_gate`, take the member below 3B confidence 0.38 | 330/415 = 79.52%, p = 0.267, **not significant** |

| condition, written before the run | result |
|---|---|
| C1 delta ≥ +20 rows | PASS (+26) |
| C2 McNemar p < 0.01 | PASS (0.000222) |
| **C3 no label worse than −3** | **FAIL — `web_search` nets −5** |
| C4 delta > 0 in ≥ 4 of 5 fold seeds | PASS (5 of 5) |

**Verdict: FAIL.** The accuracy is real and reproducible; the arm still sacrifices a class. That
is the same defect class as the `grep_only` rewrite, one digit smaller, and it is not shippable on
the strength of the headline.

## The sensitivity that changes the meaning

An adversarial review of the harness found that the fold rule alone moves a fitted arm by tens of
rows. So the same three arms were run under both rules, five seeds each, out of fold:

| arm, 2 ms, no base artifact | stratified (0,1,2,4,7) | mean | hashed | mean |
|---|---|---:|---|---:|
| `member` — tfidf_word + cue features | 314, 312, 308, 308, 307 | 309.8 | 306, 305, 307, 305, 309 | 306.4 |
| `member_scaled` — same, `feature_scale=maxabs` | **349, 351, 347, 331, 336** | **342.8** | 318, 336, 317, 330, 342 | 328.6 |
| `r_fusion` — mean@0.5 with the 3B | 351, 348, 351, 350, 350 | 350.0 | 339, 347, 352, 347, 344 | 345.8 |
| the 3B, fixed | 325 | 325.0 | 325 | 325 |

Three things fall out, in order of how much they should change a decision:

1. **`feature_scale=maxabs` moves the member by 35 rows** (314 → 349 at stratified seed 0). One
   undocumented key, larger than the entire fusion delta. Until that key is pre-registered with
   its selection cost, no part of the fusion's +26 can be attributed to fusion rather than to the
   member's configuration.
2. **The member alone beats the 3B** at 349/415 = 84.1% in 2 ms, with no base artifact, no
   recording, no server. At stratified seed 0 the fusion is 2 rows better; at seed 1 the member
   is 3 rows better (351 vs 348). The fusion's advantage over the best single cheap arm is
   **0 to 7 rows**, not 26.
3. **The fold rule is an instrument, not an implementation detail.** It moves the fusion by ~4
   rows and the member by up to 26. C4 varies seeds within one rule and therefore cannot detect
   a rule change of the same size as the effect it guards. Every artifact now records
   `dataset.cv_rule` and `grouped_cv.stratified`; quote them beside the number.

## What is established, and what is not

* **Established:** a 2 ms TF-IDF-plus-cue-features logistic arm reaches 84% out of fold on this
  corpus, against the served 3B's 78.3%, at two fold rules and five seeds. That is the cheapest
  competitive arm in the repo and it does not need a model file.
* **Established:** the 3B's own confidence is a usable correctness signal (median 0.895 on rows it
  gets right, 0.395 on rows it gets wrong, AUC 0.858), which is why any fusion form moves at all.
* **Not established:** that fusion is what buys the gain. A competing explanation — a better
  member — is worth 35 rows on its own and has not been excluded.
* **Not established:** that this survives the corpus. 86% of v3's rows contain a literal slot
  value from `tools/distill/frames.py`, and the cue table shares a source with the distiller. The
  transfer test to v2 is +2.0 points at n=150, p=0.375: same sign, no power.

## The next measurement, in one line

Pre-register the member's configuration **including `feature_scale`**, then run
`recorded|arm=floor_a` vs `member_scaled` vs `r_fusion` on 5 fold seeds × 2 fold rules with C3
attached to all three arms. Pass iff the fusion beats the best single arm by ≥ 10 rows at
p < 0.01 in both rules. `docs/plan-forward-2026-11-10.md` §5 stands as the target: until a member
is fixed before the run, every number here is a knob reading.

## What the review changed in the harness

Eleven defects, all fixed, each with a test that fails when the fix is reverted:

| | |
|---|---|
| `--fit-on X --split X` fitted and scored the same rows and reported 100% | refuses on an id overlap |
| a row that never produced a prediction was counted as a miss with no error count anywhere | `n_errors` per arm, printed in the table, stored in the summary |
| `--order` was accepted for `fusion`, whose base is a frozen replay | the refusal keys on the `replays_a_file` capability, not on a signature |
| `base=recorded~arm=grep_only` silently selected `floor_a` | the base spec expands `~` and unknown keys are refused |
| a duplicate row id in a base artifact silently overwrote the earlier row | raises |
| `--aa` on a fitted or CV reference reported a 100% flip rate | refits the A/A instance the same way, and says so |
| `--cv` left non-fitted arms in-sample beside out-of-fold ones with no marker | prints the skip and stores `grouped_cv: null` |
| a `seeds_*` condition on a run without `--cv` failed for an operational reason | refused with the reason |
| a committed artifact carried an absolute machine path and broke `test_no_personal_paths` | the dataset source is stored repo-relative |
| `fusion`'s docstring quoted another experiment's numbers | it now quotes this artifact |
| `coverage_at_precision`'s threshold did not define its set; `gate_verdict` cleared on 1 row at a 0 floor | both fixed earlier in the night, both re-verified |

The artifact was regenerated after those fixes and reproduces the same numbers to the row:
351/415, C3 FAIL, `VERDICT: FAIL`.

## The decisive follow-up: fusion against the member, pre-registered

Conditions written to `bench/results/fusion-member-prereg.json` **before** the run, with the
member's spec frozen (`vectorizer=tfidf_word|clf=logreg|features=rules|feature_scale=maxabs`) and
the pass rule requiring **both** fold rules to clear. Reference is the member, not the 3B, because
that is the competing explanation.

| rule | member (2 ms) | fusion | fusion vs member | conditions |
|---|---:|---:|---|---|
| **stratified** | **349/415 = 84.1%** | 342/415 = 82.4% | **−7 rows**, p = 0.464 | C1 −7 FAIL, C2 0.464 FAIL, C3 −12 FAIL, C4 0/5 FAIL |
| **hashed** | 318/415 = 76.6% | 334/415 = 80.5% | +16 rows, p = 0.097 | C1 +16 PASS, C2 0.097 FAIL, C3 −15 FAIL, C4 5/5 PASS |

**Verdict: FAIL under both fold rules.** Under stratified folding the fusion is *worse* than the
member by 7 rows. Under hashed folding it is 16 rows better but not significantly, and it takes
15 net rows out of one label to do it. The fusion was the plan's top-ranked direction and it does
not survive being compared to the arm it was supposed to improve on.

The member against the 3B, for completeness, and it is not clean either:

| rule | member vs 3B | p | worst label |
|---|---:|---:|---|
| stratified | **+24 rows** (fixed 34 / broke 58) | **0.016** | **−17** |
| hashed | −7 rows (fixed 55 / broke 48) | 0.555 | −19 |

So the cheapest arm in the repo beats the served 3B by 24 rows **under one fold rule and not the
other**, and it sacrifices a class while doing it. That is a lead, not a result: it needs a third
corpus and a pre-registered fix for `decide_extract` (the label it gives up) before anyone calls
the 3B replaceable.

Nothing here is a shipping decision. What is settled is negative and useful: **fusion is closed.**
