# What this tool records by default

*Assessment and change, 2026-11-04. Branch `b1-logging`. Prompted by the operator's
"idk if logs even needs to be posted like that… lets assess" — so the question is a
design question, not a permissions fix.*

Two logs shipped **on**, with no shared switch:

| log | writer | gate (before this change) | path (before) |
|---|---|---|---|
| `hops.jsonl` | `service/ti/hops/log.py` | `conf.hops_log.enabled` = `true` | `service/logs/hops.jsonl` — **relative to the service's cwd** |
| `live.jsonl` | `pi-extension/src/capture.ts` | `let enabled = true` | `<repo>/service/logs/live.jsonl` |

Both were created 644 under umask 022 (664 on this box) next to a token file that
`http/auth.py` creates 0600 and refuses at 644. The codebase knew the rule and applied it
to the one file it considered a secret.

This document answers four questions in order — *who reads each log*, *which fields that
reader needs*, *what the default should be*, *where it goes and with what mode* — then
records what changed and what it cost.

---

## 1. Who reads these logs

This is the finding, so it comes first: **`hops.jsonl` has one reader in the tree and it
takes two fields out of it.**

| log | reader | fields actually read |
|---|---|---|
| `hops.jsonl` | `tools/dataset/ingest.py::_ingest_hops` (reached via `tools/dataset/paths.py`) | `op`, `soft.intent_context` |
| `live.jsonl` | `tools/dataset/ingest.py::_ingest_live` | `intent`, `hops[0].op`, `ts`, `status` |

Everything else that mentions these files does not read them:

- `tools/distill/*` reads **generated** rows (`var/distill/`, `data/distill/`), not the
  logs. `mine.py` reads pi's own transcript corpus through the `session-insights` CLI;
  `utterances.py` labels candidates the template generator produced. The distill corpus is
  not fed by either log.
- `bench/live_e2e.py`, `bench/roundtrips.py`, `bench/demo.py` pin `hops_log.path` in their
  `TI_CONF_OVERLAY` (to keep writes out of the repo) and then assert on the **HTTP
  response**, whose `hops` carry the same `artifact_summary` field. They never open the
  file.
- `bench/replay.py` prints `hop["artifact_summary"]` from the response.
- `docs/dataset-status.md` is an analysis of the ingest report, not a second reader.

Two consequences follow.

**`artifact_summary` had no reader at all.** For every `filesys_read`, `hops.jsonl` wrote
the first 200 characters of the file. Nothing consumed them: the dataset row is
`intent → op`, and the artifact text is not part of it. A log field with no reader is the
one field that can only be a liability, and the ones with no reader were the sensitive
ones:

| field | no reader | what it contained |
|---|---|---|
| `artifact_summary` (hops) | yes | first 200 chars of whatever the hop returned — for a read, the file's opening |
| `params` (hops) | yes | `str(value)[:200]` of every argument: paths, glob patterns, grep patterns, queries |
| `cwd` (live) | yes | the session's absolute working directory |
| `error` (live) | yes | the error message verbatim, which for a filesystem error embeds the path |

**The hop log is not the dataset feeder it is documented as.** `docs/dataset-status.md`
measured the shipped log at 1,398 lines → **14** trainable records, all one label, and again
at 5,243 lines → **15** records. `tools/dataset/ingest.py`'s own docstring states the rule:
`hops.jsonl` "is an **execution trace**, not a decision log". The project already concluded
that this log cannot supervise routing; what it had not concluded is that a log which
cannot feed the pipeline and which nobody else reads should not be written by default.

A check of the opt-in writer on this tree, run against the L1 read shape this repo's own
examples use (`filesys_glob → decide_pick → filesys_read`), makes that sharper than the
old counts do. Six hop lines for two identical calls, four of them carrying the intent, and
`ingest` accepted **zero**: the same utterance appears as `filesys_glob` once and
`filesys_read` once, which the pipeline's contradiction rule reads as "no single correct
answer in the data". The glob is candidate discovery and the read is the answer
(`docs/dataset-status.md` §`live.jsonl` says the same of the live log), so for the flagship
shape the hop log's label is not merely rare — it is undefined.

## 2. Which fields are load-bearing

`hops.jsonl`, one record per executed hop:

| field | reader | verdict |
|---|---|---|
| `op` | `_ingest_hops` — the label | **load-bearing**, kept |
| `soft.intent_context` | `_ingest_hops` — the state text | **load-bearing**, kept — and now written whole (it was `str(v)[:100]`, a silent clip on the one field that matters) |
| `ts` | none | incidental, kept: it orders a trace, carries nothing |
| `kind`, `conf`, `ms` | none | incidental, kept: measurements, no user content |
| `params` | none | **removed** → `params_keys` (sorted argument *names*), which a reader of a trace wants and which cannot leak a value |
| `artifact_summary` | none | **removed** |
| other `soft` keys (`answer`, caller params) | none | **removed**; only `intent_context` survives, under its own key |

`live.jsonl`, one record per completed `useTool` call:

| field | reader | verdict |
|---|---|---|
| `intent` | `_ingest_live` — the state text | **load-bearing**, kept |
| `hops[].op` | `_ingest_live` — the label (first hop) | **load-bearing**, kept |
| `ts` | `_ingest_live` / `tools/dataset/split.py` — session grouping | **load-bearing**, kept |
| `status` | `_ingest_live` meta | kept |
| `params_keys`, `mode`, `digest_sizes`, `degraded`, `confidence`, `hops[].ms/conf`, `wall_ms`, `question_kind` | none | incidental, kept: the call's shape, sizes only, never text |
| `cwd` | none | **removed** — an absolute path with no consumer |
| `error` | none | **replaced by `error_kind`** (`timeout` / `unreachable` / `http` / `invalid` / `aborted` / `service` / `other`) — the class is what a histogram can use; the message was the only field that inlined a path |

### What did *not* change: the response

`artifact_summary` stays in the `useTool` **response** hop. It is the contract
(`pi-extension/src/contract.ts` requires it, `bench/live_e2e.py` asserts a read hop's
summary is the file's text, `tests/test_live_e2e_contract.py` pins it), and it is what makes
a hop readable in the session where it happened. This change is about what is **persisted
beyond the session**, which is a different question from what is **returned to the caller**.
Conflating the two is how a logging decision turns into an API break.

## 3. The default

Three candidates:

**On with full detail** — the status quo. Rejected. It records the operator's own goals by
default, in files any local user can read, behind an opt-out the extension forgets on
restart (`/ti capture off` set an in-memory variable). A default that cannot be durably
left is not a default; it is a policy the user has to argue with. And the measured return is
nil: ~1 % of the log's rows are trainable data and they all carry the same label.

**On with minimal fields** — the tempting middle. Rejected as the *default*, kept as the
*shape*. It fixes what is written but not that something is written: the remaining content
is still the user's own request text ("read the file we discussed" is benign; "check whether
this contract clause is enforceable" is not), and the user still has to discover a switch to
stop it. Capture of a person's work is not telemetry — nobody's product improves by watching
a stranger's first ten sessions.

**Off, opt-in, durable, minimal** — chosen. Neither log writes unless asked. Both opt-ins
are durable: `conf.hops_log.enabled` for the service (a config file, as before), and a
state file at `~/.local/state/ti/capture.json` for the extension, so `/ti capture on`
survives a restart. The record shape is the minimal one from §2 regardless.

The trade-off in one line: **the project gives up passive data collection so that its
default posture is "does what you asked and remembers nothing".** What it gives up is real
and is priced in §6.

## 4. Where a log lives, and with what mode

**Path.** `~/.local/state/ti/logs/{hops,live}.jsonl`.

The old hop path was `service/logs/hops.jsonl`, resolved against the **process cwd**, so
`ti-serve` started from `~/work/x` created `~/work/x/service/logs/` — a stray tree beside
wherever the service happened to be launched, unrelated to any project. `HOP_LOG` under the
user's state directory is where a runtime artefact belongs, and it is where this codebase
already put its one durable artefact: `http/auth.py` writes the token to
`~/.local/state/ti/http.token`. The two logs now share a directory, which is also what
`tools/dataset/paths.py` needs in order to read both by default — that default moved with
the writer, or `ingest` would silently find nothing.

**Mode.** The rule, on both sides:

| situation | behaviour |
|---|---|
| directory missing | created `0700` |
| directory wider than `0700` and ours | narrowed to `0700` |
| directory wider and **not** ours | **no write** — `os.chmod` fails, so the guarantee cannot be made (a directory someone else can modify lets them swap in a symlink and choose the destination). `HopLog.reason` says so once on stderr; the run continues. |
| log file missing | created `0600` (`os.open(..., O_CREAT, 0o600)`) |
| log file exists and is group/other-readable | narrowed to `0600` (`os.fchmod` on the opened descriptor, so there is no path race) |
| something at the path is a symlink | `O_NOFOLLOW` refuses the open; no write, `reason` set |
| the write fails for any other reason (read-only tree, full disk) | swallowed; `reason` set; **the tool call is unaffected** |

**Why narrow instead of refuse.** `http/auth.py` *refuses* a token file with mode 644, and
the difference is deliberate, not an oversight:

- A token whose mode let group read it is already compromised. `chmod` cannot un-read it, so
  continuing to use it would be pretending otherwise — hence refusal, and a message telling
  the user to delete it.
- A log is not a credential. Nobody but its owner needs it, and closing the mode *stops* the
  exposure rather than merely acknowledging it. Refusing would silently end a collection the
  user deliberately turned on — the worse of the two failures, and one the user would not
  notice.

## 5. What changed

| file | change |
|---|---|
| `service/ti/conf/defaults.json` | `hops_log.enabled: false`; path → `~/.local/state/ti/logs/hops.jsonl` |
| `service/ti/hops/log.py` | rewritten: private directory + owner-only file, narrowed if wider, `O_NOFOLLOW`, failures recorded in `reason` and never raised |
| `service/ti/service_entry.py` | the logged record: `params_keys` instead of `params`; `soft` reduced to `intent_context`, untruncated; `artifact_summary` dropped |
| `pi-extension/src/capture.ts` | default **off**; durable state file; path → `~/.local/state/ti/logs/live.jsonl`; `cwd` dropped, `error` → `error_kind`; 0600 file in a 0700 directory, widened files narrowed |
| `pi-extension/src/index.ts` | records `errorKind` instead of the error message |
| `pi-extension/scripts/capture-check.ts` | 22 → 38 cases: default state measured in a child process, mode measured with `stat`, a 0644 log narrowed, the state file 0600 |
| `tools/dataset/paths.py` | `DEFAULT_LOGS` follows the writer to `~/.local/state/ti/logs` |
| `tests/test_hop_log_privacy.py` | new: 15 tests over the default, the record shape, the mode |
| `README.md`, `docs/architecture.md`, `docs/dataset-status.md` | say what logging now does |

### Turning it on

The service's hop log (a trace of what ran, for the dataset pipeline or for a debugging
session):

```sh
echo '{"hops_log": {"enabled": true}}' > /tmp/ti-hops.json
TI_CONF_OVERLAY=/tmp/ti-hops.json ti-serve
```

The extension's session log (one line per `useTool` call):

```
/ti capture on     # writes ~/.local/state/ti/capture.json and stays on across restarts
/ti capture path   # where it writes, and which state file is in play
/ti capture stats  # count, status histogram, confidence mean/median, time window
/ti capture off    # back off, durably
```

`TI_CAPTURE=1` / `TI_CAPTURE=0` overrides the state file for one process (bench, tests);
`TI_CAPTURE_PATH` and `TI_CAPTURE_STATE` re-point the output and the state file.

### What an enabled hop record looks like now

```json
{"ts": 1793788958.437, "op": "filesys_glob", "kind": "path_list",
 "params_keys": ["cwd", "pattern"], "conf": 1.0, "ms": 0.4,
 "soft": {"intent_context": "open the alpha text file please"}}
```

and a live record:

```json
{"ts": 1793789001123, "intent": "open the alpha text file please",
 "params_keys": ["path"], "mode": "auto", "digest_sizes": {"turns": 3, "antecedents": 1, "chars": 240},
 "status": "done", "degraded": false, "confidence": 0.95,
 "hops": [{"op": "filesys_glob", "ms": 2.5, "conf": 1.0}], "wall_ms": 41,
 "error_kind": null, "question_kind": null}
```

## 6. What this costs

- **No traffic by default.** A fresh clone produces no observed rows. `tools.dataset
  ingest` on a machine that never opted in yields the 496 frozen gold records and nothing
  from runtime. That is close to what it yielded before (14–15 observed rows, all one
  label), but it is not zero, and the difference is now the user's decision instead of the
  default.
- **`cwd` and the error message are gone from the live log.** A post-hoc reader cannot tell
  which project an intent came from, or why a call failed beyond its class. Nothing read
  either field; both were the only identifying data in the record. If a future reader needs
  them, the right move is a per-session opt-in, not a default.
- **`artifact_summary` is gone from the persisted hop.** Nobody can ask a stored log "what
  did this read return". The response still carries it, per call, for the session that made
  it — and a session that needs it can be read from the transcript.
- **The non-intent soft hints are gone** (`answer`, caller params riding along). They had no
  reader; the dataset's state text was and is `intent_context` alone.
- **Old logs are not migrated.** Anything at `service/logs/` stays there; `TI_DATASET_LOGS=service/logs`
  still reads it, and `service/logs/` remains git-ignored. Files written before this change
  are readable by whatever the umask allowed, and narrowing a file on its next write does
  not retract what was already on disk.
- **`hops_log.enabled` off means the bench overlays that pin `hops_log.path`**
  (`bench/live_e2e.py`, `bench/roundtrips.py`, `bench/demo.py`) now write no hop file at
  all. They assert on the HTTP response, so nothing breaks; the pins are now inert.

## 7. What constrains the next change

- `tools/dataset/ingest.py` reads `op` and `soft.intent_context` from `hops.jsonl` and
  `intent` / `hops[0].op` / `ts` / `status` from `live.jsonl`. Those names and that nesting
  are the contract; a re-shape has to move the reader in the same commit.
- The hop record's key set is asserted in `tests/test_hop_log_privacy.py`; the live record's
  in `pi-extension/scripts/capture-check.ts` (`RECORD_KEYS`). A field added to the live
  record without a reader is how this started — add a reader first.
- Paths in shipped config and docs stay `~`-rooted: `tests/test_no_personal_paths.py` scans
  tracked files, and the repo is public.
- The dated audits (`docs/audit-2026-11-03.md`, `docs/review2-2026-11-03.md`) describe the
  behaviour as it was on their date, including `review2`'s M6 recommendation to default
  `hops_log.enabled` to `false` and to stop the test suite filling the live log. They are
  history, not specification; this document is where the current behaviour is stated.

## Verification

```
python3 -m pytest tests/ -q                     # 843 passed, 563 subtests (was 828 / 563)
node pi-extension/scripts/capture-check.ts      # 38/38 capture cases (was 22/22)
```

The mode is measured, not asserted: `tests/test_hop_log_privacy.py` creates a real log via
`HopLog` and `stat`s it (0600 in a 0700 directory), writes a 0644 file and watches the next
append narrow it, and `capture-check.ts` does the same for the extension through
`TI_CAPTURE_PATH`.
