# The grep arm: measured, and it does not ship

2026-11-10. One session, one served model (`d1-3B-Q4_K_M.gguf`, `/props` asserted before the
first call), one probe (`bench/rewrite_transfer.py`), five arms, 2,075 rows. This is the
experiment the post-rewrite plan called E4 plus the E1 floor plus an E2 control, run properly,
plus E3 (position) appended the same session.

## What was changed, and nothing else

`bench/rewrite_transfer.py` gained four arm names and no behavioural change:

| arm | description set | purpose |
|---|---|---|
| `floor_a` | `OP_DESCRIPTIONS` unchanged | A/A floor, first half |
| `grep_only` | only `filesys_grep` replaced | the treatment |
| `grep_control` | only `filesys_grep` replaced, **different words, same length** | E2: is it the clarification or just any rewording |
| `floor_b` | `OP_DESCRIPTIONS` unchanged | A/A floor, second half |
| `order_rev` | `OP_DESCRIPTIONS` unchanged, **reversed order** | E3: is it the words or the position |

The single edited string, verified byte-for-byte against `ti_bench/prompts.py`:

```
baseline : Search inside file contents for a regular expression.                          (8 words)
treatment: Search inside local file contents for a pattern or string; the answer is
           which code or text contains it.                                                 (19 words)
```

The `decide_extract` rewrite from the earlier candidate is **excluded** — it was a fit and is
not part of this test.

## The floor

| | correct | of |
|---|---:|---:|
| `floor_a` | 325 | 415 |
| `floor_b` | 326 | 415 |

**1 choice flip in 415 rows (0.24%).** The instrument is stable, and the floor is one row. Any
effect smaller than three rows is noise.

## The result

| | correct | of | |
|---|---:|---:|---|
| `floor_a` | 325 | 415 | **78.3%** |
| `grep_only` | 328 | 415 | **79.0%** |

Delta **+0.72 points**, which is **3 rows net** — exactly 3.0× the one-row floor, and the
protocol asks for *more* than 3×.

Exact McNemar on the discordant pairs: **fixed 10, broke 7, p = 0.6291.**

## The per-option ledger, which is the real finding

| label | n | base | treat | fixed | broke | net |
|---|---:|---:|---:|---:|---:|---:|
| **filesys_grep** | 52 | 36 | **46** | **10** | **0** | **+10** |
| decide_pick | 52 | 51 | 51 | 0 | 0 | +0 |
| reddit_digest | 52 | 32 | 32 | 0 | 0 | +0 |
| web_fetch | 52 | 49 | 49 | 0 | 0 | +0 |
| filesys_glob | 52 | 44 | 43 | 0 | 1 | −1 |
| filesys_read | 52 | 43 | 42 | 0 | 1 | −1 |
| decide_extract | 51 | 21 | 19 | 0 | 2 | −2 |
| **web_search** | 52 | 49 | 46 | 0 | **3** | **−3** |

The edited option gained **10 net, breaking none of its own rows**. Every gained row went
somewhere: the total stayed flat because the other seven paid for it, and the bill fell hardest
on `web_search`.

This is the coupling the plan predicted, and the broken rows are the proof rather than a
statistic:

```
web_search -> filesys_grep
  v3-0185  find writing about kalman filters outside the community threads
  v3-0226  find writing about the retry budget outside the community threads
  v3-0272  find writing about the x86 lane numbers outside the community threads
```

All three are "find writing **about** X" — a search of the world for discussion. The new
wording ends *"the answer is which code or text contains it"*, which now reads as true of them.
The model did not get sloppier; the edited description became a better fit for a question that
was never about grep.

## The pre-registered conditions, and the verdict

The plan wrote three conditions before the run. Result:

| condition | result | |
|---|---|---|
| 1. McNemar p < 0.05 | p = 0.6291 | **FAIL** |
| 2. `web_search` loses ≤ 3 rows | lost exactly 3 | PASS (at the boundary) |
| 3. untouched tools not net-negative | net −4 | **FAIL** |

**Verdict: do not ship this as a whole-dictionary edit.** The option it edits is better by 10
rows; the router is not better by any measurable amount, and one neighbouring option is worse.

What is genuinely established, and what was not before:

- The change is **not a regression** — this is not 2026-11-05 again. The instrument is stable to
  one row in 415, and the earlier "27 collateral breaks" figure does not reproduce from a
  same-session A/A baseline.
- The improvement on `filesys_grep` is **real and large** (+10/−0) and is exactly the kind of
  thing that justifies editing a description.
- The cost is **transfer, not decay**: the eight options share one fixed 100%, so a description
  that becomes a better answer-choice takes mass from a neighbour. `web_search` is the neighbour
  here, and the three rows it lost are all phrased "find writing about".
- The transfer is **wording-sensitive but always present**: both rewordings fixed essentially the
  same ten grep rows, and both paid elsewhere — one paid 7, the other 14.

So the honest recommendation is not "no". It is: **`filesys_grep`'s own routing can be fixed,
and two independent wordings agree on the fix, but it is not free and `web_search` pays.** If the
operator wants the +10, the next experiment is a **paired** rewrite — `filesys_grep` plus a
compensating `web_search` description, in one arm — with both options measured together. That is
one more arm, ~19 minutes, and it is the only way to take the grep gain without buying it from a
neighbour.

Until that is run, `service/ti/conf/defaults.json` stays untouched.

## E3: position alone — the same eight descriptions, reversed

Appended 2026-11-10, 05:08–05:29, against the same server process that served the four arms
above (started 03:44:15, never restarted; `order_rev` p50 **2 736 ms** against `floor_a`'s
2 714 ms, 0.8% apart, so the two are comparable under the protocol's 20% rule). Nothing in the
descriptions changed. `ORDER_REV` is `dict(reversed(OP_DESCRIPTIONS.items()))`
(`bench/rewrite_transfer.py:77`):

```
baseline order : filesys_read, filesys_glob, filesys_grep, decide_pick,
                 decide_extract, web_search, web_fetch, reddit_digest
reversed order : reddit_digest, web_fetch, web_search, decide_extract,
                 decide_pick, filesys_grep, filesys_glob, filesys_read
```

| | correct | of | |
|---|---:|---:|---|
| `floor_a` | 325 | 415 | **78.3%** |
| `order_rev` | 316 | 415 | **76.1%** |

Delta **−2.17 points**, **9 rows net**, exact McNemar **fixed 6, broke 15, p = 0.0784**.

**Position alone moves 34 of 415 argmaxes (8.2%).** The A/A floor moves one (0.24%), the
grep wording moves 27 (6.5%), and the same-length paraphrase moves 42 (10.1%). So the order of
the list is a **larger perturbation than the wording every arm above was about**, and its net
effect (9 rows, p = 0.078) is larger than the treatment's (3 rows, p = 0.63).

### Where it lands

| label | slot | reversed | n | base | rev | fix | brk | net |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| filesys_read | 1 | 8 | 52 | 43 | 43 | 1 | 1 | +0 |
| filesys_glob | 2 | 7 | 52 | 44 | 43 | 0 | 1 | −1 |
| filesys_grep | 3 | 6 | 52 | 36 | 35 | 3 | 4 | −1 |
| decide_pick | 4 | 5 | 52 | 51 | 51 | 0 | 0 | +0 |
| decide_extract | 5 | 4 | 51 | 21 | 19 | 1 | 3 | −2 |
| web_search | 6 | 3 | 52 | 49 | 48 | 1 | 2 | −1 |
| web_fetch | 7 | 2 | 52 | 49 | 49 | 0 | 0 | +0 |
| reddit_digest | 8 | 1 | 52 | 32 | 28 | 0 | 4 | **−4** |

Half the net loss is one class. All four `reddit_digest` breaks are the same family, and all
four go to a web op when `reddit_digest` is read **first** instead of **last**:

```
reddit_digest -> web_search   v3-0133  check the MachineLearning subreddit for the qwen3.5 release
reddit_digest -> web_search   v3-0178  check the rust subreddit for the two-pass reranker
reddit_digest -> web_fetch    v3-0148  check the LocalLLaMA subreddit for local llama.cpp serving
reddit_digest -> web_fetch    v3-0379  check the selfhosted subreddit for kalman filters
```

That is a recency effect, not a description problem: "check the {sub} subreddit for {topic}"
is answered correctly when `reddit_digest` is the last thing the model reads and wrongly when
it is the first. No wording change was ever going to find that, and it is 4 rows — more than
the entire net effect of the grep treatment.

What the per-slot chosen-rate does **not** show is a clean primacy gradient: the share of rows
answered with the option in slot 1 is 14.2% in the baseline order and 6.7% in the reversed
(n=1 permutation, so read that as a measurement of *this* reordering, not a coefficient). What
it does show is one label-by-position interaction: `web_search` is chosen on 18.1% of rows at
slot 6 and 20.5% at slot 3, and is right on 65.3% of those against 56.5%. Earlier in the list
it claims more and knows less.

### Does the wording still buy anything position cannot?

Yes, seven of the ten. Of the 10 `filesys_grep` rows the treatment fixed, `order_rev` also fixes
**3** — `v3-0064`, `v3-0182`, `v3-0400`, all "list the files that reference X" / "is X
referenced anywhere else?" — and the other **7** are the phrasing the new text was written for:

```
wording only   v3-0098  search the tree for state_max_tokens offline
wording only   v3-0366  search the tree for deprecat offline
wording only   v3-0275  search the tree for max_candidates offline
wording only   v3-0310  is _first_json_object still alive anywhere?
wording only   v3-0393  is resolve_backend referenced anywhere else?
wording only   v3-0121  is handle_stream referenced anywhere else?
wording only   v3-0233  is ChoiceAnswer referenced anywhere else?
position too   v3-0064  list the files that reference resolve_backend
position too   v3-0182  is pack referenced anywhere else?
position too   v3-0400  list the files that reference tau_lo
```

`order_rev` buys three fixes of its own
(`v3-0367`, `v3-0005`, `v3-0155`) while breaking fifteen, so it is not a substitute for the
wording — it is a second, independent lever with its own bill.

### What this changes about how to read the rest of the repo

1. **Paired comparisons are safe; absolute numbers are not.** Every earlier arm here held the
   order fixed, so an order effect cancels in a delta. But **78.3% was always this order's
   78.3%**, not the model's: reverse the list and it is 76.1%. Any level quoted without an
   order is quoted to about ±2 points of a term nobody measured until now. The confidence
   interval covers zero, so this is a *warning*, not a proven order effect: one permutation,
   p = 0.078, and 8! orders exist.
2. **A description edit is no longer the only explanation for a routing fix.** Three of the
   ten `filesys_grep` fixes come from reading grep six slots later instead of three. The
   diagnosis "the model routes on the noun" survives; the inference "therefore the description
   must change" is weaker than it was this morning.
3. **The next experiment should hold order constant and test it separately.** The paired
   rewrite the recommendation above asks for should be two arms: `grep + compensated
   web_search` in the baseline order, and the same thing in a seeded shuffled order. Otherwise
   the next +3 rows might be position again.
4. **This is E3 of the plan, half-filled.** The plan asked for three seeded permutations; this
   is one deliberate reversal. A reversal is the strongest single permutation (it moves every
   option), so 8.2% is an upper bound on what a random shuffle would move, not an estimate of
   it.

### What it does to the verdict above

Nothing. `grep_only` still fails conditions 1 and 3 and still does not ship. What it does is
put a number on something the verdict assumed was zero: order alone *costs* 9 rows (p = 0.078)
and flips more argmaxes than the treatment does. The recommendation is unchanged in direction
and sharper in form: **before spending another arm on description text, run one arm that only
reorders the list**, because it is cheaper, it cannot make the router semantically worse, and
on this evidence it is worth as much as the wording.

## Reproduction

```
# server
./extern/llama.cpp/build/bin/llama-server -m models/d1-3B-Q4_K_M.gguf \
    --host 127.0.0.1 --port 8080 --jinja -fa on -c 4096 -t 8

# arms, in this order, in one session
for arm in floor_a grep_only floor_b grep_control order_rev; do
  python3 bench/rewrite_transfer.py --arm $arm --expect-model d1-3B-Q4_K_M.gguf
done

python3 bench/grep_arm_report.py     # the tables above, from rows.jsonl
```

Wall clock measured on this laptop: 18m40s per 415-row arm, 2.6–3.0 s/row; `order_rev` took
20m59s at 3.0 s/row. No money involved.
