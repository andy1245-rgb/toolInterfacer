# toolInterfacer — Spec 1.0

Status: agreed design (2026-10-16 discussion). This document is the source of
truth for what gets built and in what order.

## 1. Problem

pi's LLM issues every tool call itself. Read→search→fetch→verify work costs
4–10 model round trips (seconds each), mostly moving tokens instead of
information. A local decision model (Liquid d1-3B today: 91.4% tool routing at
p50 243ms, calibrated confidence, zero generated tokens; a fine-tuned
qwen3.5-4b later) can do tool selection, slot filling, and result verification
at ~250ms per decision — if the scaffolding around it is good.

## 2. Mental model

- The LLM calls one registered pi tool: `useTool(intent, params?, mode?)`.
- `intent` is plain English. `params` is a freeform dict — LLM-supplied
  parameters (paths, URLs, "must be from this week") plus context hints.
- The service classifies intent completeness:
  - **L0 passthrough** — params fully specify a single tool → schema-validate,
    execute, return. No decision model in the loop (~ms).
  - **L1 slot-fill one hop** — vague params, one tool → candidates assembled
    from disk/session digest → decision model picks → execute → return.
  - **L2 pipeline templates** — compound intents ("research X", "what does
    r/… say") → authored step graphs, decision model animates the choice
    nodes, CLIs and pi tools execute.
  - **L3 model-planned DAG** (v2) — decision model composes the plan itself;
    L2 templates become known-good plan fragments.
  - **L4 browser** (future) — adapter slot reserved (`agent-browser`), not wired.
- Ask-back: when confidence or verification fails after best-effort, the tool
  returns `{status:"need_input", question...}` — one LLM round trip, capped.
- Destructive pi tools (bash/write/edit) stay native until trust is earned.
  v1 domain: read/glob/grep + the web/reddit CLI stack.

## 3. Tool contract

```
useTool(intent: string, params?: object, mode?: "auto"|"raw"|"plan")
→ { status: "done"|"need_input"|"error",
    result?, degraded?, assumptions?,
    sources?, confidence?,
    hops: [{step, op, ms, conf, artifact_summary}...] }
```

- `mode:"plan"` returns the decision chain (resolved plan + per-step conds)
  without executing — the offline benchmark mode.
- `mode:"raw"` returns un-summarized results (LLM escape hatch).
- `params` keys that match the resolved step's schema are injected as real
  args; every other key is passed to the decision model as soft context.
- `confidence` is present only when the run measured one: it is the lowest
  measurement among the hops that made one, and it is absent — not `1.0` — when
  nothing was measured or the run errored. `hops[].conf` is `null` for an op
  that measured nothing. See `docs/confidence-sources.md`.
- `hops[].conf` is a measurement, never a default: a p_max below `gate` is the
  evidence ask-back runs on, so a fabricated number there is a fabricated
  reason not to ask.
  Unknown keys never fail a call (open-context semantics).

## 4. Ask-back policy

One governing rule: **ask the LLM only when the answer lives in conversation
history, not on disk.** The LLM's context contains antecedents the decision
model lacks; everything else the service can find itself.

Triggers (the complete v1 list):
1. Route confidence < gate after the heuristic micro-gate.
2. Slot confidence < gate **after candidate enumeration** (disk globs, digest
   mentions, top search hits — d1 picks among candidates first).
3. `noul` verification failed twice on a completed step.
4. Contradiction between artifacts the result depends on.

Ask-back rules:
- Question is always structurable: `choice` (candidates listed) > `confirm` >
  `free` (rare). Payload always includes `hops` + `artifacts` so the LLM
  answers once and the loop resumes with no redo.
- Budget: `max_asks = 2` per `useTool` call (config). After cap → return
  `status:"done", degraded:true, assumptions:[...]` with the best-guess
  result. A degraded result has information value; an abort does not.
- Never ask when route confidence ≥ gate: a confident miss surfaces its own
  evidence in `hops`, cheaper to correct than to pre-check.

Gates (config, starting values, tuned in Phase 5):
- route ≥ 0.7 auto-run; slots ≥ 0.7; noul ≥ 0.75.

## 5. Decision-model wall

All backends implement the same primitives (see `ti/decide/primitives.py`):

- `choice(state, instructions, criteria{id: description}) → {choice,
  probabilities, confidence}` — criteria carry descriptions (bare labels hurt
  d1 routing, per doc 10 of the research).
- `noul(state, question) → p`
- `score(...)` (optional), `extract(...)` (needle2 slot extraction, later phase)

Backends (one file each under `ti/decide/backends/`), selected in config:
- `d1_systemone` — llama.cpp ≥ b11500 `POST /v1/systemone` (the v1 backend)
- `jev_api` — hosted/localjev systemone-compatible endpoint (thin, reserved)
- `logit_read` — any local LLM, option letters A–Z → top_logprobs mapping
  (the Jev-Style recipe; the adapter the future qwen3.5-4b finetune plugs into)
- `heuristic_micro` — URL/path/scheme pattern gate; exists only to keep d1
  out of trivial calls; measured in Phase 5, deleted if it doesn't pay.

Abstraction rule: pipelines and the runner never import a backend directly.
Backend selection, plus every tuning specific (top-k values, gate numbers,
caps, backends per op, retry counts), lives in `conf/defaults.json`. Plan
templates state *what* happens; config decides *how much*.

## 6. Module map

```
service/ti/
  core/        runner (op→artifact→gate cycle), artifacts, gates, budget
  planner/     inspector (intent→meta), templates/ (research, reddit_digest,
               disk_lookup), free.py (L3 placeholder)
  decide/      primitives.py (the wall), backends/
  ops/         op_api.py (registration + step schema), web/ (search, fetch),
               reddit/digest.py, filesys/ (read, glob, grep)
  context/     packer.py (state assembly + token budgeting),
               session_digest.py (pi transcript digest consumer)
  policy/      askback.py, confidence.py
  hops/        log.py (JSONL hops log — the future 4B finetune dataset)
  http/        api.py — stdlib HTTP: POST /v1/useTool, POST /v1/plan, GET /health
  conf/        defaults.json — every knob, one place
pi-extension/src/
  useTool.ts       registerTool("useTool"); hides nothing in v1; fast-path beta
                   (read/glob/grep family) hides native once trusted
  bridge.ts        HTTP client to the service
  session_push.ts  rolling session digest (~400 tokens, recent-weighted)
  lifecycle.ts     spawn/kill service, health poll
```

Deps policy: Python core is stdlib-only (no fastapi, no numpy). L2 template
params render safe shell-outs to fixed script paths (no intent text in shell
strings where avoidable; manifest-driven argument lists otherwise).

## 7. Research pipeline (v1's headline L2 template)

1. `planner.inspector` classifies scope: quick_lookup | full_research |
   reddit_centric | disk_centric
2. `extract/queries` — 3–6 search queries from intent (+ digest mentions)
3. `search` over configured CLI backends → merge, dedupe by URL
4. `decide:pick` — one choice over title+snippet list → top-k (config)
5. `fetch` loop over chosen URLs; per page `noul:is_relevant` ≥ gate, else
   skip; stop after k good pages (config)
6. optional `reddit` cross-check step, gated by the step-1 classification
7. `assemble` — per-source claim digest + link + confidence; `hops` attached

Estimated wall: ~250ms × ~8 decisions + CLI time ≈ 15–40s vs minutes of LLM
round trips — the claim Phase 4 benchmarks.

## 8. Phases and acceptance criteria

- **P0 — skeleton + spec + docs.** All modules stubbed with real interfaces;
  `tests/test_skeleton.py` imports every module and the registry works.
  Done = committed and pushed.
- **P1 — basic loop (model-free).** runner + artifacts + gates + budget +
  fixture-player decide backend + filesys ops + http api +
  conf. Acceptance: fixture test — a `disk_lookup` plan runs end to end in
  `mode:"plan"` and `"auto"` with recorded decide-responses and zero network;
  bench/replay prints hops, confidences, wall time.
- **P2 — d1-3B live.** llama.cpp ≥ b11500 serving d1-3B Q4_K_M; live
  `d1_systemone` backend. Acceptance: live routing probe over ≥50 held-out
  pi-tool utterances: zero malformed responses, p50 ≤ 1s on this box, calibrated
  conf recorded to hops log.
- **P3 — pi extension wired.** useTool registered; bridge; session digest;
  lifecycle. Acceptance: in a live pi session, `useTool("read the file we
  discussed")` resolves via digest + candidates and returns done with no
  ask-back; ask-back path demonstrated with a degraded/need_input case.
- **P4 — L2 templates.** research + reddit_digest templates wired to the real
  CLI adapters. Acceptance: research on 3 seeded topics returns a sourced
  digest; benchmark vs a scripted LLM-driver baseline reports wall-clock and
  hop counts.
- **P5 — tuning + dataset.** gates tuned from hops log; heuristic micro-gate
  measured (keep or delete); shadow-scoring mode (extension logs LLM-call vs
  decision-agreement) accumulating the finetune dataset.

## Divergences from this spec

Written 2026-11-03, and added **after** the fact: the body above is the design of record and
is left as it was agreed. Where the implementation has moved away from it, this is the list.
Each row names who is right — the code in seven, this spec in one, neither in one.

| § | the spec says | the code does | which is right |
|---|---|---|---|
| §2, §4 | ask-back returns `need_input` and the loop resumes — one LLM round trip, capped | over HTTP the question rides in the response body and the answer comes back as `params.answer` on a **second** call: `service_entry.use_tool(..., ask_via_response=True)`, set by `http/api.py`. The resuming form exists only for a direct caller that passes `on_ask` | the code — the transport has no mid-request channel, so the spec's one-round-trip resumption is not available on the wire |
| §3 | the response carries `sources?` | no top-level `sources` is ever emitted. A digest's sources are inside the digest artifact, which arrives as `result` (`ops/research/assemble.py`) | the code |
| §3 | `mode:"raw"` returns un-summarized results | `mode` is compared only against `"plan"`; `"raw"` runs as `"auto"` (`service_entry._route`). Nothing tests it | neither — an unimplemented escape hatch. It should either be implemented or struck from the contract |
| §3 | `confidence` is "the lowest measurement among the hops that made one" | `service_entry._route_conf` takes the minimum over **decide** hops plus a resolved ask-back, and only when `status` is `done`. A deterministic op's confidence (a read reports 1.00) does not enter it | the code, and it is the stricter rule: the spec's wording would report 1.0 for an L0 passthrough and for every L1 listing, which is the fabricated number §3 exists to forbid |
| §5 | four backends: `d1_systemone`, `jev_api`, `logit_read`, `heuristic_micro` | nine are registered: `jev_api` never shipped; `openrouter`, `pair`, `cascade`, `classical`, `rule_extract` and `fixture` were added (`decide/pair.py`, `decide/cascade.py`, `decide/backends/`) | the code |
| §5 | `extract(...)` is "needle2 slot extraction, later phase" | shipped as `rule_extract`: deterministic regexes, no model, and it measures no confidence (`hops[].conf` is `null`) | the code — the primitive exists, the needle2 extractor never did |
| §6 | the module map names `pi-extension/src/useTool.ts`, and `decide/backends/` for every backend | tool registration lives in `pi-extension/src/index.ts` (`useTool.ts` does not exist); `pair` and `cascade` live in `decide/`, not `decide/backends/`, because they route between backends rather than implement one | the code |
| §7 | step 1 classifies scope as `quick_lookup \| full_research \| reddit_centric \| disk_centric` | there is no such enum. `planner/inspector.py` applies six ordered keyword rules and yields a level plus a template; the four scope names collapse into those | the code — and the rule layer is itself a known gap (`TODO.md` §3), since a real classifier was the point of the phase |
| §8 | **P2** is "d1-3B live" | the repo also uses "P2" for "route the plan choice through the decision model" (`service/ti/planner/inspector.py`, `TODO.md` §3) | this spec — §8's phase name is the original one; the other usage is a module docstring's shorthand and the two should not be read as the same milestone |

Phase acceptance, checked against the tree rather than against intent:

- **P0** passes (`tests/test_skeleton.py` imports every module).
- **P1** passes (`bench/replay.py` runs a `disk_lookup` plan end to end with the fixture
  backend and prints hops, confidences and wall time).
- **P2** passes on its numbers — 150 held-out utterances, zero malformed responses in the
  recorded lanes, p50 153–163 ms — but the *routing* half of the ambition, a model choosing
  the route, is the open item in `TODO.md` §3, not this phase.
- **P3** is met on the service side only. `bench/live_e2e.py` drives HTTP ingress → plan →
  decide → ops against a real model (`docs/live-e2e-2026-11-03.md`), and the extension's
  contract check runs against a stub, but the criterion says *a live pi session*, and no
  in-repo artifact records one: registration, the digest and the `session_start` spawn are
  typechecked, not run.
- **P4** is half met: the research template returns a sourced digest (`bench/demo.py`
  scene 3, `tests/test_research_template.py`) and the two-arm benchmark exists
  (`docs/roundtrips-2026-11-03.md`, wall clock and hop counts), but there is one recorded
  research intent, not the three seeded topics the criterion asks for.
